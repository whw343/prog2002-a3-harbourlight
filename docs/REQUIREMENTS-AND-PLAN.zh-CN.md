## 4. 文档矛盾、缺失及处理方式

1. **报名接口矛盾。** 第 4 页称不要求操作 registration 的接口，第 5 页却要求报名页调用接口插入报名。必须有创建报名接口才能闭环；据此将其列为必做。不把报名修改/删除自动扩为必做。
2. **分类管理范围矛盾。** 第 2 页总述涉及分类管理，第 4 页明确分类操作接口非必需，第 5–6 页管理端仅详细要求活动 CRUD。基础范围为动态分类列表及活动分类选择；分类 CRUD 作为可选扩展，向 tutor 确认。
3. **压缩包数量笔误。** 第 8 页写 2 个，却明确列出 clientside、adminside、api 三个文件名。先按三个独立源码包准备，最终核对提交入口。
4. **报告规格不完整。** 第 8 页明确 project documentation required，但本文件没有 A3 报告模板、字数或章节要求。不默认沿用 A2 模板；先积累架构、API、测试和部署文档，待取得 A3 模板再映射。
5. **截止日期已过。** PDF 第 1 页写 2026-10-12 23:59 AEST/AEDT，当前客户端日期为 2026-10-18。以 Blackboard 或获批延期为准；不能假设仍在正常提交期。这里不编排时间表。
6. **用户身份未定义。** 无需 USER 表或登录，无法可靠证明真实身份。建议使用去除首尾空格并统一大小写后的邮箱作为课程范围内的用户标识，并说明其局限。
7. **视频提交单位不够明确。** 第 7 页要求突出个人贡献、最长 15 分钟。按每人能展示自身贡献准备材料，再确认是一人一段/一份还是合并一份；不能把共同录制或只录一人的做法写成已获许可。
8. **AI 规则未知。** A2 对话曾记录用户称未发布规则，但不能外推为 A3 全面许可。取得课程当前规定后如实披露实际使用。

## 6. 建议的实现设计（尚未实现）

### 数据与一致性

报名表建议字段：id、event_id、full_name、email、email_normalized、phone、ticket_quantity、registered_at。事件 ID 与规范化邮箱构成唯一键；外键采用限制删除，不级联删除报名；报名时间由服务器记录。

票数为正整数并设明确合理上限，前后端共同验证。保留票价与筹款字段的明确语义：登记票数不代表真实完成支付，不自动把票款当作已筹捐款；本题没有要求支付网关、真实收款或出票系统。

删除保护不只在按钮中判断：数据库外键、服务端错误映射共同兜底。测试报名与删除竞争、重复点击和并发重复报名，确认最终状态一致。UTC 存储与 Australia/Sydney 展示保持统一，跨日与夏令时转换单独核验。

### API 草案

| 方法与路径 | 作用 |
| --- | --- |
| GET /api/events | 保留公众列表和组合筛选 |
| GET /api/categories | 分类选择数据 |
| GET /api/events/:id | 公众活动详情及公开报名字段 |
| POST /api/events/:id/registrations | 校验并创建报名 |
| GET /api/admin/events | 全状态活动管理列表 |
| GET /api/admin/events/:id | 管理详情及该活动的报名数据 |
| POST /api/admin/events | 新增活动 |
| PUT /api/admin/events/:id | 更新活动 |
| DELETE /api/admin/events/:id | 无报名才允许删除 |

路径为建议，不是题目强制格式。使用参数化 SQL，成功创建返回 201；无效输入 400、不存在 404、重复报名或不允许删除 409；服务错误不泄露 SQL、密码及堆栈。公共详情使用固定少量查询，避免逐报名查询。

公众报名列表显示所有记录的必要字段，如展示名、票数、日期，不公开邮箱和电话；管理端才返回必要联系方式。课程允许不实现认证，因此 /admin 路径本身不构成权限控制：公网演示只用虚构数据，若要实际运营必须补认证授权。CORS 不能替代身份认证。

页面均处理加载、成功、无记录、无效 ID、提交失败及重试；避免旧筛选响应覆盖新结果。禁用提交中的重复按钮，数据库唯一约束作为最终保护。管理保存后读回，报名后回详情验证新记录出现并正确排序。

### 加分项决策

优先考虑 Open-Meteo：增加活动经纬度，展示活动日期对应的可用天气；超出预报范围、超时或错误时给出明确不可用状态，不影响报名。不能把今天的天气当作数月后的活动天气。

官方资料：https://open-meteo.com/en/docs （查询于 2026-10-18）。标准预测存在时间范围限制，具体参数以实施时文档为准；PDF 示例中的天气码“2003”疑似笔误，实施时按官方天气码表核对。

AngularJS 在题目中是可选加分，并非必做，也不能用现代 Angular 冒充 AngularJS。官方确认自 2022 年 1 月结束支持：https://docs.angularjs.org/ 。默认保留课程允许的原生 JS，先完成所有核心要求；如选择 AngularJS，应在开发初期决定并在客户端和管理端正确使用，接受迁移和维护成本，不在交付前仓促改写。

## 9. 有意义的验收场景

1. 10+ 初始报名可在相应详情页看到，跨活动互不混入，按报名时间倒序。
2. 同邮箱报同一活动第二次被阻止；大小写及首尾空格不绕过约束；同人报另一活动成功；并发请求仅一条落库。
3. 缺字段、错误邮箱、0/负数/小数/过大票数、非法活动 ID 被拒；失败不留下半条数据。
4. 新增活动、修改日期/分类/状态后，公众站与管理端数据一致；过去/暂停活动的报名规则明确且服务端执行。
5. 无报名活动可删除；有报名活动返回清晰冲突，所有数据保留；并发报名/删除不破坏关系。
6. 公共 API 不返回邮箱电话；输入不能作为脚本执行；SQL 参数化；客户端篡改不能绕过后端验证。
7. 日期/地点/分类的单项及组合筛选、清空、直接打开详情、刷新、返回和空结果均正常。
8. 桌面与手机、键盘操作、至少两个可用浏览器检查；网络失败和恢复有实际反馈。
9. 天气超范围和服务故障不阻断其他功能；只在实施该项后验收。
10. 两台个人 cPanel 环境分别从最终 SQL 和打包代码部署，并在公网复验；不能仅提供首页截图。

不预设测试数量，不把预期结果记录为通过结果。保存实际环境、日期、范围、结果及限制。破坏性测试使用隔离数据库。
